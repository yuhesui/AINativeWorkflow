\section*{Part I --- Autonomous ML research result (maximum 4 pages)}
\textbf{Status: protocol complete; qualifying result pending.}

\subsection*{1. Research question}
Long-horizon language-agent systems increasingly use plans, subagents, memory, and verification, but it remains unclear whether a persistent hierarchical control layer improves task execution enough to justify its overhead. We test a mechanism-level hypothesis: compared with a competent flat workflow using the same ChatGPT Main and Claude Code executor, does AI-Native Workflow better preserve accumulated requirements and localize recovery on tasks whose specifications or live state evolve over time?

The method is itself an agent-management system rather than a new base model. Its canonical hierarchy is
\[
\text{Goal}\to\text{Plan}\to\text{Phase}\to\text{DIC}\to\text{EPS}\to\text{Prompt/Run}\to\text{Action}.
\]
A Phase has one durable multi-view DIC. \texttt{REQUESTS.md} stores concrete goals, while \texttt{PLAN.md} stores prompt dependencies, parallel subagents, merge points, and conditional repair branches. EPS instances materialize that plan against current state. Verification returns accept, repair, replan, or escalate.

\subsection*{2. Frozen paired study}
The evaluation is deliberately small because it is a workshop proof of concept executed with subscription resources rather than an API-scale sweep. ChatGPT Plus is Main in every run. Claude Code authenticated through Claude Pro A is the primary executor; Claude Pro B is reserved for the pre-declared hard-task replications.

We compare two conditions. \textbf{F (Flat)} uses the same ChatGPT+Claude stack and permits ordinary planning, iterative debugging, and local tests, but omits the package-resident DIC/EPS hierarchy, persistent Request ledger, dependency-local invalidation, and structured recovery state. \textbf{W (Workflow)} uses the full AI-Native system. F is therefore a strong non-hierarchical baseline rather than a one-shot prompt.

\subsection*{3. Outcomes and evidence discipline}
The primary evidence consists of official benchmark reward/pass, SlopCodeBench strict pass rate by checkpoint, regression/erosion, rework, repair scope, Main turn count, executor prompt/run count, and wall time. Token counts are included only when the subscription surfaces expose them reliably. With five task families we report all runs and paired/checkpoint traces; we do not turn the study into a population-level significance claim.

All scored evidence must enter a machine-readable run store. Manuscript tables are generated from raw Harbor/verifier records; no aggregate number is hand-copied from a chat summary. Failed attempts and negative results are retained. This is particularly important for AutoMLR because eligibility depends on a real research result, not on a narrative that an autonomous system ``did research.''

\subsection*{5. Formal support and limitations}
Under complete declared dependencies and version-bound evidence, a repair that changes keys $\Delta$ need invalidate only the dynamic impact cone of nodes that read those keys and their descendants; the cone is worst-case tight given footprint information alone. If a persisting observable fault is missed at each gate with conditional probability at most $\alpha$, survival through $k$ gates is at most $\alpha^k$. Conversely, if the evidence observation aliases a successful and unsuccessful state, no evidence-only verifier can attain both zero false acceptance and zero false rejection. These statements motivate the mechanism but do not substitute for empirical evidence.

\subsection*{1. System boundary and persistent authority}
\textbf{[HUMAN REWRITE REQUIRED]} The system stores canonical state in \texttt{.ai-workflow/STATE.json}. A human approves a multi-phase Plan. Main owns integration, architecture and publication decisions; Theory owns formal/novelty work; Experiment owns benchmark methodology and evidence. Ordinary machine execution occurs below the Plan boundary. Material objective, scientific-claim, protocol, destructive/external, credentials/private-system, paid-compute, release and submission changes are explicit escalation categories.

\subsection*{2. DIC, execution plan and EPS}
\textbf{[HUMAN REWRITE REQUIRED]} Each Phase has one multi-view DIC. README gives the overall summary; REQUESTS records specific goals and acceptance targets; PLAN records actual prompt/run nodes, dependencies, parallel subagent batches, merge/review points and conditional branches. ARCHITECTURE and TEST\_MATRIX are optional views, and users can register custom views. The EPS is not another high-level plan: it instantiates durable Plan nodes just in time with current context, model surface, attempt, outputs and stop conditions.

\subsection*{3. Verification and recovery}
\textbf{[HUMAN REWRITE REQUIRED]} Verification produces accept, repair, replan or escalate. Local deterministic checks occur automatically; fresh independent review is reserved for material claims/release boundaries. A repair normally preserves the DIC and supersedes only affected EPS/run instances. Phase reports are mandatory, flat, capped at ten files by default, and include key merged raw evidence as well as human synthesis.

\section*{Part III --- Reflections (maximum 1 page)}
\begin{center}\textbf{HUMAN AUTHORSHIP / REWRITE REQUIRED BEFORE SUBMISSION}\end{center}
A compliant final Part III should be written after the qualifying study and should address at least four questions: (1) which scientific decisions the autonomous system made that the human authors would otherwise have made; (2) where the system optimized the wrong proxy or required intervention; (3) whether persistent contracts and raw evidence made the result easier to audit or merely increased bureaucracy; and (4) what should remain a human judgment even if the agent can execute most research steps.

One provisional lesson can be stated factually from the current package: externalizing requests, execution graphs, evidence and repair history makes it easier to identify \emph{where} human intervention occurs. That is useful for disclosure, but it does not itself establish autonomous research quality. AutoMLR eligibility should therefore be treated as an empirical property of the completed research trajectory, not a label attached to an agent harness.
